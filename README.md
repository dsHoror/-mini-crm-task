# Объекты и задачи

Тестовый мини-CRM 2B Studio: объекты и задачи на этих объектах. Сейчас в репозитории каркас клиента и схема Supabase. Экраны не ходят в базу, визуальная система не проектировалась, на Vercel проект не выкладывался.

## Стек

- Vite, React, TypeScript
- Mantine
- React Router
- `@supabase/supabase-js`, только anon key
- Позже статический деплой на Vercel: preset Vite, каталог `dist`

Версии зафиксированы в `package.json`. Для сборки нужен Node.js 22.

## Запуск

```bash
cp .env.example .env.local
npm install
npm run dev
```

Сборка: `npm run build`. Проверка линтером: `npm run lint`.

Без `.env.local` приложение открывается, экраны остаются заглушками, клиент Supabase не создаётся. Значения ключей в интерфейс не выводятся.

Маршруты:

| Путь | Экран |
| --- | --- |
| `/login` | Login |
| `/` | ObjectsList |
| `/objects/:objectId` | ObjectDetail |
| `/tasks/:taskId` | TaskDetail |
| `/my-tasks` | MyTasks |

## Переменные

В клиент попадают только две переменные, обе с префиксом `VITE_` (они видны в браузере):

- `VITE_SUPABASE_URL`
- `VITE_SUPABASE_ANON_KEY`

Ключ `service_role` в репозиторий не кладётся и в клиент не подключается. Anon key публичный по устройству Vite, доступ к строкам держится на RLS.

## Миграции

Файлы лежат в `supabase/migrations` и применяются по имени:

1. `20261105120000_schema.sql` — типы, таблицы, триггер профиля.
2. `20261105120100_rls_and_status_rpc.sql` — RLS, `is_manager()`, `change_task_status()`, запрет прямой смены статуса и записи истории.

Нужна роль владельца таблиц, не anon key. В SQL Editor Supabase вставить файлы по порядку. Через CLI, когда проект привязан:

```bash
supabase db push
```

Локальный стек Supabase перед этим должен уже содержать схему `auth`. Регистрацию в нём тоже надо выключить (`enable_signup = false` в конфиге Auth).

Проверка ограничений, скрипт сам делает `ROLLBACK`:

```bash
psql "$SUPABASE_DB_URL" -v ON_ERROR_STOP=1 -f supabase/tests/rls_negative.sql
```

`$SUPABASE_DB_URL` — строка подключения Postgres (роль владельца), не anon key. Скрипт создаёт временных пользователей в `auth.users`.

Обязаны падать три случая:

- чужая задача: исполнитель вызывает `change_task_status` для задачи другого исполнителя;
- запрещённый переход, в том числе `rework` без комментария;
- правка `task_status_history`: `INSERT`, `UPDATE` и `DELETE` и от `authenticated`, и от владельца таблицы, пока задача ещё существует.

## Регистрация и роли

Самостоятельная регистрация в проекте Supabase выключена: Authentication → Providers → Email → Allow new users to sign up = off. На фронт это не перекладывается.

Пользователей создаёт администратор в Dashboard. Триггер `app_private.handle_new_user` заводит строку в `profiles` с ролью `executor`. Менеджера назначают вручную в SQL Editor, от владельца базы, не из клиента:

```sql
update public.profiles
set role = 'manager'
where id = '<uuid из auth.users>';
```

Подписанный пользователь не может сменить `role`: на колонку нет `UPDATE`, а триггер отклоняет смену, если JWT принадлежит `authenticated`. Своё `full_name` менять можно.

## Доступ

`public.is_manager()` — `security definer`, чтобы политики не зацикливались на RLS `profiles`.

| Таблица | Менеджер | Исполнитель |
| --- | --- | --- |
| `objects` | все операции | `SELECT` только объектов, где у него есть задача |
| `tasks` | все операции, кроме прямой смены `status` | `SELECT` только своих (`assignee_id = auth.uid()`). Чужой `UPDATE` отклоняется RLS |
| `task_status_history` | `SELECT` всех строк | `SELECT` истории своих задач |
| `profiles` | чтение всех, правка своего `full_name` | то же |

Статус меняется только через `change_task_status(p_task_id, p_to_status, p_comment)`. Функция проверяет роль, что исполнитель является исполнителем этой задачи, и что переход есть в графе. В историю пишутся `changed_by = auth.uid()` и `changed_at = now()`.

| Откуда | Куда | Исполнитель-assignee | Менеджер |
| --- | --- | --- | --- |
| `new` | `in_progress` | да | да |
| `in_progress` | `review` | да | да |
| `review` | `accepted` | нет | да |
| `review` | `rework` | нет | да, комментарий обязателен |
| `rework` | `in_progress` | да | да |

`accepted` конечный. Новая задача создаётся только со статусом `new`. Комментарий к переходу в `rework` не может быть пустым или из одних пробелов.

Прямой `UPDATE tasks.status` закрыт дважды: у `authenticated` нет права на эту колонку, а триггер пускает смену только из RPC (роль владельца функции и служебный флаг транзакции). У `task_status_history` нет политик и грантов на запись. Удаление задачи менеджером удаляет её историю каскадом; отдельное удаление строк истории запрещено.

## Допущения

- «Свои» задачи исполнителя — это `assignee_id = auth.uid()`. Авторство доступа не даёт. Неназначенная задача исполнителю не видна, статус ей меняет менеджер.
- Исполнитель видит объект, если на нём есть хотя бы одна его задача. Задачи коллег на этом объекте ему не отдаются.
- Любой `authenticated` читает `full_name` и `role` в `profiles`, чтобы позже показать исполнителя. Email живёт в `auth.users` и в профиль не копируется.
- Ошибка «чужая задача» (`only the assignee can change this task`) отличается от «задача не найдена». Это внутренний инструмент, UUID снаружи не перебираются.
- `service_role` обходит RLS и может менять роли. Статус и история от него тоже закрыты триггером, но ключ всё равно нельзя класть в клиент или в git: с ним читаются все строки.
- Владелец таблиц в SQL Editor может снять триггер. Обычный `UPDATE` статуса без RPC у владельца тоже падает, пока триггер включён. Пользователям приложения SQL-логин не выдавать.
- Смена исполнителя не пишется в `task_status_history`.
- История начинается с первой смены статуса, отдельной строки «создана» нет.
- Адрес и название объекта обязательны и не могут быть пустыми.
- Экраны пока не вызывают `supabase.rpc('change_task_status', ...)`. Типы аргументов лежат в `src/lib/database.types.ts`.

## Как это собрано

Каркас подготовлен в Cursor агентом на модели Grok (Grok Bot). Это черновик схемы и заглушек, а не ручной аудит безопасности. Перед боевыми данными человек должен просмотреть миграции, политики RLS и `change_task_status`. Зелёный прогон `supabase/tests/rls_negative.sql` проверяет перечисленные запреты, он не заменяет ревью.

## Чего в этой версии нет

- Подключённый вход через `supabase.auth` и загрузка объектов и задач.
- Макет интерфейса.
- Деплой. На Vercel позже выбрать preset Vite. Отдельно проверить, что прямые адреса `/objects/...` и `/tasks/...` не отвечают 404.
