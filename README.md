# Объекты и задачи

Тестовый мини-CRM 2B Studio: объекты стройки и задачи на этих объектах. Клиент на Vite ходит в Supabase только с anon key. Статус задачи меняется через `change_task_status`.

## Стек

- Vite, React, TypeScript
- Mantine
- React Router
- `@supabase/supabase-js`, только anon key
- Позже статический деплой на Vercel: preset Vite, каталог `dist`

Версии зафиксированы в `package.json`. Для сборки нужен Node.js 22.

## Запуск

```bash
cp .env.example .env.local
npm install
npm run dev
```

В `.env.local` только две переменные:

- `VITE_SUPABASE_URL`
- `VITE_SUPABASE_ANON_KEY`

Ключ `service_role` в репозиторий не кладётся и в клиент не подключается. Anon key публичный по устройству Vite, доступ к строкам держится на RLS.

Сборка: `npm run build`. Проверка линтером: `npm run lint`.

Без `.env.local` открывается экран входа с предупреждением, запросы в базу не уходят. Значения ключей в интерфейс не выводятся.

Самостоятельная регистрация в проекте Supabase выключена: Authentication → Providers → Email → Allow new users to sign up = off.

## Тестовые учётки

Файл `supabase/seed.sql` создаёт демо-пользователей, три объекта и задачи в разных статусах. Его выполняет владелец базы после миграций, не anon key:

```bash
psql "$SUPABASE_DB_URL" -v ON_ERROR_STOP=1 -f supabase/seed.sql
```

Тот же файл можно вставить в SQL Editor. Повторный запуск ничего не меняет, если эти почты уже есть. Пароли только для тестового стенда, на боевой проект скрипт не накатывать.

| Почта | Пароль | Имя | Роль |
| --- | --- | --- | --- |
| `ivanov@2bstudio.test` | `demo-ivanov` | Иванов И.И. | постановщик (`manager`) |
| `petrov@2bstudio.test` | `demo-petrov` | Петров П.П. | исполнитель (`executor`) |

В сиде: «ЖК Северный, корп. 3» (ул. Ленина, 12) с пятью задачами, «Склад №2» (пр. Мира, 45) и «Офис А» (ул. Садовая, 8). У «Офис А» задача без исполнителя, поэтому Петров этот объект не видит.

Пользователей вне сида по-прежнему создаёт администратор в Dashboard. Триггер `app_private.handle_new_user` заводит строку в `profiles` с ролью `executor`. Менеджера назначают вручную в SQL Editor:

```sql
update public.profiles
set role = 'manager'
where id = '<uuid из auth.users>';
```

## Экраны

| Путь | Экран |
| --- | --- |
| `/login` | Вход по почте и паролю |
| `/` | Список объектов |
| `/objects/:objectId` | Карточка объекта и его задачи |
| `/tasks/:taskId` | Карточка задачи, действия по статусу, история |
| `/my-tasks` | Задачи, где `assignee_id` — текущий пользователь |

Шапка: «Объекты», «Мои задачи», имя, роль, выход. На узком экране те же разделы и «Ещё» (имя и выход) в нижней панели.

Постановщик создаёт и правит объекты и задачи, назначает исполнителя, на статусе «На проверке» принимает задачу или возвращает на доработку. Комментарий к доработке обязателен. Редактирование и удаление задачи доступны, пока она «Новая».

Исполнитель видит объекты, где у него есть задачи, и только свои задачи. Переходы: «Новая» и «На доработке» → «В работе» → «На проверке».

Пустые списки, ошибки загрузки и ошибки форм показываются на экране. Пока данные грузятся, на месте списка показывается состояние загрузки.

## Переменные

В клиент попадают только `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`.

## Миграции

Файлы лежат в `supabase/migrations` и применяются по имени, до сида:

1. `20261105120000_schema.sql` — типы, таблицы, триггер профиля.
2. `20261105120100_rls_and_status_rpc.sql` — RLS, `is_manager()`, `change_task_status()`, запрет прямой смены статуса и записи истории.
3. `20261106064800_restrict_history_and_status_rules.sql` — `ON DELETE RESTRICT` для истории и задач объекта, граф статусов только для назначенного исполнителя на трёх рабочих переходах, длина `objects.name` и `tasks.title` 1..200.

Нужна роль владельца таблиц, не anon key. В SQL Editor Supabase вставить файлы по порядку. Через CLI, когда проект привязан:

```bash
supabase db push
```

Локальный стек Supabase перед этим должен уже содержать схему `auth`. Регистрацию в нём тоже надо выключить (`enable_signup = false` в конфиге Auth).

Проверка ограничений, скрипт сам делает `ROLLBACK`:

```bash
psql "$SUPABASE_DB_URL" -v ON_ERROR_STOP=1 -f supabase/tests/rls_negative.sql
```

`$SUPABASE_DB_URL` — строка подключения Postgres (роль владельца), не anon key. Скрипт создаёт временных пользователей в `auth.users` и не пересекается с учётками из `supabase/seed.sql`.

Обязаны падать:

- чужая задача: исполнитель вызывает `change_task_status` для задачи другого исполнителя;
- запрещённый переход, в том числе `rework` без комментария и попытка менеджера сделать `new → in_progress`, `in_progress → review` или `rework → in_progress`;
- правка `task_status_history`: `INSERT`, `UPDATE` и `DELETE` и от `authenticated`, и от владельца таблицы;
- удаление задачи, у которой уже есть история, и удаление объекта, на котором есть задачи;
- `tasks.title` или `objects.name` длиннее 200 символов.

## Регистрация и роли

Подписанный пользователь не может сменить `role`: на колонку нет `UPDATE`, а триггер отклоняет смену, если JWT принадлежит `authenticated`. Своё `full_name` менять можно. В интерфейсе имя не редактируется.

## Доступ

`public.is_manager()` — `security definer`, чтобы политики не зацикливались на RLS `profiles`.

| Таблица | Менеджер | Исполнитель |
| --- | --- | --- |
| `objects` | все операции | `SELECT` только объектов, где у него есть задача |
| `tasks` | все операции, кроме прямой смены `status` | `SELECT` только своих (`assignee_id = auth.uid()`). Чужой `UPDATE` отклоняется RLS |
| `task_status_history` | `SELECT` всех строк | `SELECT` истории своих задач |
| `profiles` | чтение всех, правка своего `full_name` | то же |

Статус меняется только через `change_task_status(p_task_id, p_to_status, p_comment)`. Клиент вызывает эту RPC и не пишет в колонку `tasks.status`. Функция проверяет роль, что исполнитель является исполнителем этой задачи, и что переход есть в графе. В историю пишутся `changed_by = auth.uid()` и `changed_at = now()`.

| Откуда | Куда | Исполнитель-assignee | Менеджер |
| --- | --- | --- | --- |
| `new` | `in_progress` | да | нет |
| `in_progress` | `review` | да | нет |
| `review` | `accepted` | нет | да |
| `review` | `rework` | нет | да, комментарий обязателен |
| `rework` | `in_progress` | да | нет |

`accepted` конечный. Новая задача создаётся только со статусом `new`. Комментарий к переходу в `rework` не может быть пустым или из одних пробелов.

В интерфейсе постановщик принимает задачу и возвращает её на доработку. Кнопок «Взять в работу» и «Отправить на проверку» у него нет. Исполнитель двигает «Новая» / «На доработке» → «В работе» → «На проверке». Правка и удаление задачи на экране есть только у постановщика и только в статусе «Новая».

Прямой `UPDATE tasks.status` закрыт дважды: у `authenticated` нет права на эту колонку, а триггер пускает смену только из RPC (роль владельца функции и служебный флаг транзакции). У `task_status_history` нет политик и грантов на запись. Удаление задачи с историей отклоняется (`task_status_history.task_id` — `ON DELETE RESTRICT`); задачу без истории удалить можно. Объект с задачами удалить нельзя (`tasks.object_id` тоже `RESTRICT`). Отдельное удаление строк истории запрещено. Если удаление упирается в эти связи, диалог подтверждения показывает текст ошибки и не закрывает экран.

## Допущения

- «Свои» задачи исполнителя — это `assignee_id = auth.uid()`. Авторство доступа не даёт. Неназначенная задача исполнителю не видна. Сдвинуть её из `new` может только назначенный исполнитель, поэтому без исполнителя она остаётся новой. Менеджер принимает задачу или возвращает её на доработку со статуса `review`.
- Исполнитель видит объект, если на нём есть хотя бы одна его задача. Задачи коллег на этом объекте ему не отдаются.
- Любой `authenticated` читает `full_name` и `role` в `profiles`, чтобы показать исполнителя. Email живёт в `auth.users` и в профиль не копируется.
- Ошибка «чужая задача» (`only the assignee can change this task`) отличается от «задача не найдена». Это внутренний инструмент, UUID снаружи не перебираются.
- `service_role` обходит RLS и может менять роли. Статус и история от него тоже закрыты триггером, но ключ всё равно нельзя класть в клиент или в git: с ним читаются все строки.
- Владелец таблиц в SQL Editor может снять триггер. Обычный `UPDATE` статуса без RPC у владельца тоже падает, пока триггер включён. Пользователям приложения SQL-логин не выдавать.
- Смена исполнителя не пишется в `task_status_history`.
- История начинается с первой смены статуса, отдельной строки «создана» нет.
- Адрес и название объекта обязательны и не могут быть пустыми. `objects.name` и `tasks.title` — от 1 до 200 символов (`char_length`). В формах то же ограничение, `maxLength={200}`.
- На вайрфреймах у задач есть срок («до 15.11»). В схеме колонки даты нет, поэтому в интерфейсе срока нет.

## Как это собрано

Каркас схемы, RLS и заглушек экранов подготовлен в Cursor агентом на модели Grok (Grok Bot). Рабочий интерфейс поверх каркаса тоже собран в Cursor с помощью ИИ-ассистента. Это черновик, а не ручной аудит безопасности. Перед боевыми данными человек должен просмотреть миграции, политики RLS, `change_task_status` и вызовы клиента. Зелёный прогон `supabase/tests/rls_negative.sql` проверяет перечисленные запреты, он не заменяет ревью.

## Чего в этой версии нет

- Деплой. На Vercel позже выбрать preset Vite и проверить, что прямые адреса `/objects/...` и `/tasks/...` не отвечают 404.
- Регистрация, восстановление пароля, уведомления, роль администратора, тёмная тема.
- Срок задачи из вайрфреймов: в таблице `tasks` нет такой колонки.
- Смена своего отображаемого имени из интерфейса. Колонка `full_name` для этого открыта политикой, экран не делался.
